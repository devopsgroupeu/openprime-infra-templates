# Infrastructure

Generated by OpenPrime. Two Terraform stacks and the ArgoCD manifests they install.

```
terraform/aws/         VPC, EKS, databases, IAM — the AWS layer
terraform/kubernetes/  ArgoCD and the app-of-apps that installs everything else
argocd/                Application definitions and Helm values
```

Both stacks keep their state in the S3 bucket created for this environment, with S3
native locking. Nothing here needs a DynamoDB table.

## Deploying

Push to `main` runs `plan`. To apply, run the **Terraform Deployment** workflow manually
and pick `apply`. The AWS stack goes first; the Kubernetes stack follows.

### If this repository is on GitLab

The pipeline is `.gitlab-ci.yml`. Two GitLab defaults can stop it:

- **CI/CD variables are protected by default**, so they only reach protected branches.
  On an unprotected branch `validate:aws` and `validate:k8s` fail with
  `No valid credential sources found`, because the backend check initialises the state backend.
  Protect the branch you deploy from (Settings → Repository → Protected branches), or
  clear "Protect variable" on `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and
  `TF_VAR_git_repo_ssh_key`.
- **New gitlab.com accounts must verify their identity** (phone or card) before GitLab
  runs any pipeline. Until then the pipeline shows as failed with 0 jobs. Self-managed
  GitLab instances do not ask for this.

## Destroying

Run the same workflow with `destroy`. It tears down Kubernetes first, then AWS — and the
AWS teardown only starts if the Kubernetes one succeeded. That order is deliberate:
in-cluster controllers create load balancers and security groups that Terraform never
recorded, and if they are still running when the VPC is deleted, the VPC deletion fails
and the leftovers keep costing money.

### Your databases are protected, and the teardown relaxes that on purpose

RDS and Aurora ship with `deletion_protection = true`, so nothing can delete them by
accident. `terraform destroy` on its own cannot get past that — destroy only plans
deletions, it never changes an attribute first, so AWS refuses `DeleteDBInstance` and the
failure cascades to the DB subnets, the internet gateway and finally the VPC.

The destroy job therefore runs one `terraform apply` before the teardown, which clears
deletion protection and sets `apply_immediately` so the change takes effect now rather
than at the next maintenance window. You do not need to edit anything.

**A final snapshot is taken by default.** If you want the database gone with no
recoverable copy, tick **Destroy without taking a final DB snapshot** when you start the
workflow. That data cannot be recovered afterwards.

The snapshot survives the destroy and is not free. Delete it yourself once you are sure
you no longer need it.

### What destroy does not remove

The Terraform state bucket for this environment is left in place on purpose, so a
half-finished teardown can be resumed. Remove it by hand when you are finished with the
environment.
